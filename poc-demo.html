  1. cs.js runs on EVERY website (manifest: "*://*/*")
  2. cs.js listens to window.postMessage — ANY page can send messages

  4. cs.js forwards messages to bg.js (the privileged background)
  5. bg.js executes the command and sends results back
  6. Results come back via postMessage("*") — attacker receives them

Step 2: Talk to Extension (The Core Vulnerability)

How: postMessage with spoofed bus identity — NO origin validation

The content script (cs.js) listens to window.addEventListener("message")

It checks ONLY: e.$bus === true && e.appName === "__app_hrp"

Step 3: Execute JavaScript in ANY Tab (RCE)

How: engine.executeJs → chrome.scripting.executeScript(MAIN world)

The bg.js handler engine.executeJs(tabId, code) calls:

// bg.js — _executeJs handler (ACTUAL DECOMPILED CODE):

async _executeJs(tabId, code) {
  await chrome.scripting.executeScript({
    target: { tabId: tabId },         // ← ANY tab
    world: "MAIN",                    // ← full page context
    args: [code],
    injectImmediately: true,
    func: e => {
      try {
        new Function(e)()             // ← executes attacker's code
      } catch(t) {
        // If CSP blocks new Function(), use DOM bypass:
        if (t.message.includes("Content Security Policy")) {
          const t = document.createElement("div");
          t.setAttribute("onreset", e);    // ← CSP bypass trick
          t.dispatchEvent(new Event("reset"));
        }
      }
    }
  })
}

// WHAT THIS MEANS:
// An attacker sends: engine.executeJs(tabId, "document.cookie")
// bg.js runs chrome.scripting.executeScript in that tab
// The code runs with FULL page privileges
// Even CSP-protected sites get bypassed via the onreset trick

Why Browser Security Doesn't Protect Against This

SECURITY MECHANISM              WHY IT FAILS HERE
─────────────────────────────────────────────────────────────────
Same-Origin Policy              postMessage is DESIGNED to be cross-origin.
                                The vulnerability is that HARPA doesn't check
                                event.origin — it accepts from ANY origin.

Content Security Policy         HARPA's bg.js has a FALLBACK that bypasses CSP:
                                  1. Try new Function(code) first
                                  2. If CSP blocks it → use onreset DOM trick
                                Also: HARPA disables Trusted Types on ALL sites.

Manifest V3 restrictions        MV3 removed eval() from background scripts, but
                                HARPA uses chrome.scripting.executeScript with
                                world:"MAIN" + new Function() INSIDE the injected
                                function. The eval happens in the PAGE context,
                                not the service worker — MV3 doesn't block this.

Site Isolation                  Doesn't matter — chrome.scripting.executeScript
                                runs in the TARGET tab's process. The extension
                                has permission to inject into ANY tab.

Extension permissions prompt    User already granted permissions at install time.
                                The user trusted the extension, not the attacker's
                                website. The website BORROWS the extension's power.

Network monitoring (DevTools)   postMessage is IN-PROCESS. It never hits the
                                network. DevTools Network tab shows NOTHING.
                                Only the final exfiltration fetch is visible.
